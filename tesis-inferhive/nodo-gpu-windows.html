InferHive · alta de nodo

Sumar una GPU de una PC con Windows al clúster

El paso a paso completo, de una PC recién instalada a un nodo Ready que se suma solo cada vez que la PC prende. Está armado a partir de lo que se hizo con ah-compute (GTX 1650 SUPER, 31/10 al 1/11/2026) y de lo que hoy hacen los instaladores del repositorio.

Mapa: qué corre dónde

k3s no tiene agente nativo para Windows. El nodo es una distro Ubuntu dentro de WSL2: Windows aporta el hardware, el driver y el arranque, y todo lo de Kubernetes vive en Linux. La GPU llega a Linux por /dev/dxg (la ruta de WSL), no por /dev/nvidia*.

Regla para leer las fases: las etiquetas Windows WSL Clúster dicen dónde se corre cada comando, y lo hace el instalador marca lo que el comando del portal ya resuelve.

Dos rutas de alta

Ruta A · comunitaria

Comando del portal

  • Desde /nodos se genera irm …/join/<código>/windows | iex (un solo uso, vence en 1 hora).
  • El nodo se llama gpuc-*, entra en cuarentena y el calificador lo aprueba solo.
  • Para calificar pide al menos 7,5 GB de VRAM y 5 tok/s. Una GPU de 4 GB no pasa.
  • Fases que cubre: 2 (parcial), 3, 4, 5, 6 y 7 (con el problema del keepalive).
Ruta B · nodo core (la de ah-compute)

Manual, con nombre fijo

  • El nombre tiene que estar en la lista exacta coreName de k8s/25-nodos-autoguardia.yaml. Si no está, el kubelet queda rechazado en CREATE y repite "node not found".
  • Esa lista solo se aplica con k8s/fix-ahora-6.sh guard, y lo corre una persona.
  • Token: el agent-token o uno de un solo uso (k3s token create --ttl 1h), nunca el token del server.
  • Es reservable por alumnos y no pasa por el calificador.

Acceso SSH a Windows

Windows · PowerShell adminopcional, solo para operar a distancia

La plataforma no lo necesita. Sirve para que vos (o Claude) operen la PC desde Linux.

PowerShell (admin)
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic
# shell por defecto: PowerShell en vez de cmd
New-ItemProperty -Path "HKLM:\SOFTWARE\OpenSSH" -Name DefaultShell `
  -Value "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -PropertyType String -Force
# la regla del firewall aplica al perfil Private: la red de casa tiene que estar como privada
Set-NetConnectionProfile -InterfaceAlias "Wi-Fi" -NetworkCategory Private
  • Si el usuario es administrador, la clave pública va en C:\ProgramData\ssh\administrators_authorized_keys (no en ~\.ssh\authorized_keys), con permisos solo para Administrators y SYSTEM.
  • En Linux, el alias win-tesis en ~/.ssh/config con IdentitiesOnly yes.
Truco para correr cosas dentro de WSL por SSH

PowerShell rompe los pipes dentro de wsl -c "…". Conviene escribir un .sh local, copiarlo con scp a C:/Users/<usuario>/ y correrlo con wsl -d Ubuntu-24.04 -u root -e bash /mnt/c/Users/<usuario>/x.sh.

Verificar

ssh win-tesis hostname responde sin pedir contraseña.

Virtualización en BIOS y driver NVIDIA

BIOS + Windows
  1. Activar la virtualización del CPU: SVM Mode en AMD, Intel Virtualization Technology (VT-x) en Intel. En la ASUS TUF B450M se entra con Supr. Sin esto WSL2 no arranca.
  2. Instalar el driver NVIDIA de Windows actualizado. Trae el soporte CUDA para WSL: dentro de WSL no se instala ningún driver de Linux.
  3. Plan de energía: que no se suspenda nunca con corriente.
PowerShell
nvidia-smi                               # modelo, VRAM y versión del driver
powercfg /change standby-timeout-ac 0    # no suspender con corriente
# reiniciar directo al BIOS (desde Windows):
shutdown /r /fw /t 0
Verificar

nvidia-smi muestra la placa y en el Administrador de tareas, pestaña Rendimiento, figura "Virtualización: habilitado".

WSL2 con Ubuntu 24.04 y systemd

WindowsWSLel instalador hace .wslconfig y systemd
PowerShell (admin), una vez
wsl --install -d Ubuntu-24.04
# reiniciar, abrir la distro una vez y crear el usuario
%UserProfile%\.wslconfig (Windows)
[wsl2]
networkingMode=mirrored
vmIdleTimeout=-1
memory=8GB          # dejarle a Windows al menos la mitad
/etc/wsl.conf (dentro de WSL)
[boot]
systemd=true
[network]
hostname=ah-compute

Después, wsl --shutdown y volver a abrir la distro.

  • systemd=true: sin systemd no hay servicios para tailscaled ni k3s-agent.
  • vmIdleTimeout=-1 mantiene viva la VM, no la distro. La distro sigue apagándose sola (ver fase 7).
Verificar

Dentro de WSL: ps -p 1 -o comm= da systemd y nvidia-smi muestra la placa (viene de /usr/lib/wsl/lib).

El .wslconfig también se puede ver y editar desde la aplicación WSL Settings (menú Inicio): cada ajuste de la aplicación es una línea del archivo.

3

nvidia-container-toolkit y su endurecimiento

WSLel instalador lo hace con --install-toolkit

Se instala desde el repositorio apt de NVIDIA antes de k3s: k3s detecta el runtime nvidia al arrancar. Si el toolkit se instala después, hay que reiniciar k3s-agent.

/etc/nvidia-container-runtime/config.toml
accept-nvidia-visible-devices-envvar-when-unprivileged = false
accept-nvidia-visible-devices-as-volume-mounts = true

Por qué: sin esto, cualquier pod podría tomar la GPU con solo poner NVIDIA_VISIBLE_DEVICES, sin pedir nvidia.com/gpu. El calificador lo comprueba en la ruta comunitaria.

Verificar

nvidia-ctk --version responde y el archivo tiene los dos valores.

Tailscale dentro de WSL

WSLel instalador lo hace

Va dentro de la distro: el agente k3s anuncia la IP 100.x y flannel sale por la interfaz tailscale0, que tiene que existir en Linux. Es una decisión de este clúster. Tailscale recomienda en general instalarlo solo en el host Windows y advierte que tenerlo activo en Windows y en WSL2 a la vez rompe el tráfico. Por eso en esta PC no hay cliente de Tailscale en Windows (verificado el 10/11/2026).

bash (WSL, root)
curl -fsSL https://tailscale.com/install.sh | sh
tailscale up --hostname=ah-compute --accept-dns=false
tailscale ping <IP Tailscale del control plane>
  • La URL de login la aprueba el dueño del tailnet.
  • En la consola de Tailscale, desactivar la expiración de clave de la máquina. Si no, se cae del tailnet a los 180 días.
Verificar

tailscale ip -4 devuelve una 100.x y el ping al control plane responde.

5

Raíz como mount compartido (wsl-rshared)

WSLel instalador lo hace si detecta WSL2

WSL2 monta / como private. Con eso los volúmenes hostPath fallan ("path / is mounted on / but it is not a shared or slave mount", visto en node-exporter) y los contenedores privilegiados, como el device plugin, se cuelgan al arrancar.

bash (WSL, root)
cat >/etc/systemd/system/wsl-rshared.service <<'EOF'
[Unit]
Description=Make / a shared mount (WSL2 default is private; kubelet needs rshared)
DefaultDependencies=no
Before=k3s-agent.service
After=local-fs.target
[Service]
Type=oneshot
ExecStart=/usr/bin/mount --make-rshared /
RemainAfterExit=yes
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload && systemctl enable --now wsl-rshared.service
Verificar

findmnt -no PROPAGATION / da shared.

6

Agente k3s

WSLel instalador lo hace con el código del portal
Antes de unirlo (ruta B)

El nombre del nodo (ah-compute) ya tiene que estar en coreName y aplicado con k8s/fix-ahora-6.sh guard. En la ruta A el nombre es gpuc-* y entra con los taints de cuarentena.

bash (WSL, root)
mkdir -p /etc/rancher/k3s
TSIP=$(tailscale ip -4 | head -1)
cat >/etc/rancher/k3s/config.yaml <<EOF
node-ip: $TSIP
flannel-iface: tailscale0
kubelet-arg:
  - fail-swap-on=false
EOF
read -rs K3S_TOKEN        # se pega el token: no se muestra ni queda en el historial
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.36.4+k3s1 \
  K3S_URL=https://<IP Tailscale del control plane>:6443 K3S_TOKEN="$K3S_TOKEN" sh -s - agent
unset K3S_TOKEN
  • node-ip y flannel-iface: tailscale0 son obligatorios. Sin eso los pods del nodo no llegan a los de la nube (por ejemplo, no tienen DNS).
  • Con ah-compute se instaló el binario de la release de GitHub (verificando su sha256) más un k3s-agent.service escrito a mano. Funciona igual que el instalador.
  • El token es un secreto: se copia por un canal privado y nunca se pega en un chat ni se guarda en un archivo.

El archivo real de ah-compute agrega node-name y reservas para que los pods no dejen sin recursos a Windows ni al propio WSL: max-pods=30, system-reserved=cpu=500m,memory=1Gi, kube-reserved=cpu=250m,memory=512Mi y eviction-hard=memory.available<500Mi,nodefs.available<10%.

Verificar

systemctl is-active k3s-agent da active y desde el clúster kubectl get node ah-compute -o wide muestra el nodo con InternalIP 100.x.

Arranque automático (keepalive)

Windows · PowerShellel instalador la registra, pero mal

WSL apaga la distro pocos segundos después de que termina el último proceso wsl.exe, y con ella systemd, tailscaled y k3s-agent. Pasa al cerrar una sesión SSH y pasa cuando la PC arranca y nadie abre WSL. La solución es una tarea programada que deje un wsl.exe vivo para siempre.

Lo que hoy está mal

La tarea pcoin-wsl-keepalive de ah-compute, igual que la que crean los instaladores (app/onboarding.py:106 y join/windows/pcoin-host.ps1:157), es Interactive con disparador al iniciar sesión. Si la PC arranca sola o después de una actualización, el nodo queda NotReady hasta que alguien inicia sesión. Verificado el 1/11 y de nuevo el 10/11/2026: la PC prendida, la tarea en Ready sin correr y el nodo NotReady. En ah-compute se corrigió el 10/11/2026 con la versión de abajo; los instaladores siguen igual.

Versión correcta: principal S4U y disparador al arranque

PowerShell (admin)
$a  = New-ScheduledTaskAction -Execute "wsl.exe" -Argument "-d Ubuntu-24.04 -u root --exec sleep infinity"
$tr = @((New-ScheduledTaskTrigger -AtStartup), (New-ScheduledTaskTrigger -AtLogOn))
$p  = New-ScheduledTaskPrincipal -UserId $env:USERNAME -LogonType S4U -RunLevel Limited
$s  = New-ScheduledTaskSettingsSet -ExecutionTimeLimit 0 -RestartCount 99 `
        -RestartInterval (New-TimeSpan -Minutes 1) -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries
Register-ScheduledTask -TaskName "pcoin-wsl-keepalive" -Action $a -Trigger $tr -Principal $p -Settings $s -Force
Start-ScheduledTask -TaskName "pcoin-wsl-keepalive"
Start-Sleep 30; wsl -l --running
  • S4U ejecuta la tarea como tu usuario sin sesión abierta y sin guardar la contraseña. La distro de WSL está registrada por usuario, por eso la tarea tiene que correr con ese mismo usuario y no con SYSTEM.
  • Probado el 10/11/2026 en esta PC: después de reiniciar sin iniciar sesión, los wsl.exe arrancaron en la sesión 0 a los 18 segundos del arranque y el nodo quedó Ready en alrededor de un minuto. Si en otra PC S4U no levanta WSL, la alternativa es "Ejecutar tanto si el usuario inició sesión como si no" con la contraseña guardada (el Programador de tareas pide la contraseña por pantalla). Esa opción deja de andar si cambia la contraseña de Windows.
  • wsl --shutdown mata la tarea: después hay que relanzarla con Start-ScheduledTask.
Verificar (la prueba real)

Reiniciar la PC sin iniciar sesión, esperar 2 minutos y comprobar desde Linux: kubectl get node ah-compute da Ready.

Lado clúster: GPU visible y prueba

Clúster · adminruta A: lo hace el calificador

Ruta B (core): desde tu máquina, con el kubeconfig de admin.

bash (tu Linux)
./deploy/bootstrap.sh gpu ah-compute
# etiquetas acceso.impulsate.lat/gpu=true y reservable=true, taint gpu=reservado:NoSchedule;
# el DaemonSet del device plugin arranca en el nodo
kubectl get node ah-compute -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'   # espera: 1
Pod de prueba (admin)
apiVersion: v1
kind: Pod
metadata: { name: gpu-smoke, namespace: default }
spec:
  restartPolicy: Never
  runtimeClassName: nvidia
  nodeSelector: { kubernetes.io/hostname: ah-compute }
  tolerations: [{ key: gpu, operator: Equal, value: reservado, effect: NoSchedule }]
  containers:
    - name: smi
      image: nvidia/cuda:12.4.1-base-ubuntu22.04
      command: ["nvidia-smi"]
      resources: { limits: { nvidia.com/gpu: 1 } }
  • Para Grafana y la alerta GpuNodeOffline: GPU_NODE en config.env y volver a correr ./deploy/bootstrap.sh monitoring.
  • Ruta A: el portal pasa de "Installing" a "Quarantined (qualifying)" y el calificador corre cada 2 minutos. La primera vez tarda de 10 a 20 minutos porque baja el modelo.
Verificar

kubectl logs gpu-smoke muestra la placa. Los pods del nodo (device plugin, node-exporter, dcgm-exporter, alloy) están Running. Al terminar, kubectl delete pod gpu-smoke.
