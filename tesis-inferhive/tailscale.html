Tailscale en la práctica

Lo necesario para operar nodos de un clúster k3s híbrido sobre Tailscale: control plane en la nube, nodos GPU en casa y uno de ellos dentro de WSL2 en una PC con Windows.

Lectura: 5 min · Verificado contra la documentación oficial y tailscale 1.104

01Conceptos base

Tailscale arma una red privada entre máquinas usando WireGuard, sin abrir puertos ni administrar un servidor VPN. Esa red se llama tailnet y cada máquina que se suma es un dispositivo (la consola los lista en Machines).

Cada dispositivo recibe una IP del rango 100.x.y.z que no cambia mientras siga registrado, aunque la máquina se mueva de red. Si se lo borra del tailnet y vuelve a entrar, recibe otra. Para un nodo de k3s eso significa que la IP 100.x sirve como --node-ip estable.

Hay dos planos. El servicio de coordinación maneja identidades, claves y políticas, pero no transporta tráfico: los paquetes viajan cifrados con WireGuard entre los dispositivos. Cuando no se logra una conexión directa (NAT estricto, firewalls), el tráfico pasa por un servidor DERP, un relay que reenvía paquetes ya cifrados; funciona, pero con más latencia.

MagicDNS registra un nombre DNS para cada dispositivo. Es cómodo en una laptop, pero en un nodo del clúster implica que Tailscale toma la configuración DNS del sistema. En este proyecto los nodos usan --accept-dns=false para que la resolución del host (y por lo tanto la de kubelet y los pods) no dependa de Tailscale; es una decisión del proyecto, no una regla de la documentación, que presenta esa opción como forma de dejar de aceptar el DNS del tailnet en un dispositivo.

02Dos formas de sumar una máquina

Login interactivo

tailscale up sin key imprime una URL (“To authenticate, visit:”). La máquina entra al tailnet de la cuenta que abre y aprueba esa URL. Si la abre alguien con otra cuenta, el dispositivo termina en otro tailnet.

Auth key

Se pasa una auth key generada en la consola y la máquina se autentica sola, sin que nadie abra un navegador. Es la opción para servidores, scripts y nodos remotos.

03Auth keys

Al crear una key en la página Keys de la consola se eligen sus atributos (fuente):

One-off o reusable
Una key one-off conecta un solo dispositivo. Una reusable conecta todos los que se quiera hasta que vence o se revoca, por eso es la más delicada si se filtra.
Ephemeral
El dispositivo se borra solo tras un rato sin actividad (hoy, entre 30 y 60 minutos). Ideal para CI o contenedores; mala idea para un nodo, que desaparecería del tailnet después de un apagón.
Pre-approved
Si el tailnet tiene aprobación de dispositivos, la máquina queda aprobada al entrar.
Tags
El dispositivo toma la identidad de los tags de la key en lugar de la de una persona.

Hay dos vencimientos distintos. La key vence entre 1 y 90 días después de creada (90 si no se indica). La clave del dispositivo (node key) expira por defecto a los 180 días y obliga a reautenticar; la expiración se desactiva por máquina con Disable key expiry en Machines. Que venza o se revoque la key no desautoriza a los dispositivos que ya entraron con ella.

Las keys empiezan con tskey-auth y el secreto se muestra completo una sola vez: hay que guardarlo en un gestor de secretos en ese momento. La página Keys sigue listando las keys activas y las revocadas o vencidas recientes. Tratarla como una contraseña: si se pasa directo en la línea de comandos, puede quedar en el historial de la shell.

04Tags y tagOwners

Los tags identifican máquinas que no son de una persona, como servidores. Un dispositivo con tag deja de pertenecer a la cuenta que lo dio de alta (tiene tags o usuario, no ambos), así que no se cae si esa persona se va, y su expiración de clave queda desactivada por defecto.

Antes de usar un tag hay que declararlo en tagOwners del archivo de política. Después se asigna con una key que lo trae o desde Machines, con la opción Edit tags del menú del dispositivo.

// archivo de política del tailnet (fragmento)
"tagOwners": {
  "tag:k3s-node": ["autogroup:admin"]
}

Recomendación: dos keys separadas. Una para nodos (reusable, no efímera, preaprobada, con tag:k3s-node) y otra para laptops, sin tag y con vencimiento corto.

05Roles de usuario

Resumen de User roles:

  • Member: usa la red según la política, pero no entra a la consola; no aprueba, no borra, no toca expiraciones.
  • Admin: puede hacer cualquier acción de la consola.
  • IT admin: administra usuarios y máquinas; puede aprobar, renombrar y borrar dispositivos.
  • Network admin: administra la configuración de red; puede aplicar cualquier tag.

Generar auth keys requiere ser Owner, Admin, IT admin o Network admin, según la página de auth keys. La documentación no detalla qué rol puede desactivar la expiración; como es una acción de la consola, un Member no puede.

06Comandos útiles

Referencia: CLI de Tailscale; los flags de up que no figuran ahí están en el código de up.

# Conectar un nodo con key, nombre fijo y sin DNS de Tailscale
sudo tailscale up --auth-key=file:/ruta/a/la-key --hostname=gpu-node-01 --accept-dns=false
# --auth-key=file:...  lee la key de un archivo (no aparece en ps ni en el historial)
# --reset              vuelve a su valor por defecto todo flag no indicado
# --timeout=60s        no esperar para siempre a que tailscaled quede Running
tailscale status                      # estado propio y de los peers
tailscale status --self --peers=false # solo esta máquina
tailscale ip -4                       # la IP 100.x de esta máquina
tailscale ping control-plane          # ping por Tailscale; dice si fue directo o por DERP
tailscale netcheck                    # diagnóstico de la red física local
tailscale whois 100.64.0.1            # qué máquina y usuario tienen esa IP
sudo tailscale set --accept-dns=false # cambia una sola preferencia, sin repetir las demás
tailscale file cp informe.txt gpu-node-01:  # enviar un archivo a otro dispositivo

tailscale down desconecta pero conserva el login: un up posterior reconecta sin key. tailscale logout desconecta e invalida el login, así que el próximo up pide autenticar de nuevo (y en un nodo efímero lo borra en el acto).

Pegar una key sin dejar rastro

Correr las líneas de a una. Si se pegan juntas, read toma la línea siguiente como si fuera la key.

  1. Leer la key sin mostrarla; pegarla y pulsar Enter:
    read -rs TSKEY
  2. Comprobar que se cargó (el largo, no el valor; 0 significa que no entró):
    echo ${#TSKEY}
  3. Conectar:
    sudo tailscale up --auth-key="$TSKEY" --hostname=gpu-node-01 --accept-dns=false
  4. Borrar la variable:
    unset TSKEY

07Caso real: un nodo en NotReady durante días

Un nodo GPU del clúster pasó a NotReady y después a Unknown, y quedó así varios días. Conviene diagnosticar en cadena, de abajo hacia arriba, porque cada eslabón depende del anterior:

  1. distro / servicio corriendo
  2. →
  3. Tailscale logueado
  4. →
  5. k3s-agent conecta
  6. →
  7. nodo Ready

La máquina estaba encendida, pero tailscale status mostraba Logged out, y el log de k3s-agent repetía failed to get CA certs … context deadline exceeded: el agente no llegaba al control plane porque la ruta hacia él era la IP 100.x.

tailscale status --self --peers=false
journalctl -u k3s-agent -n 50 --no-pager
kubectl get nodes -o wide

Se resolvió volviendo a loguear con una auth key pasada como archivo temporal (--auth-key=file:) y borrando el archivo después. El nodo conservó su IP 100.x, lo esperable porque seguía registrado, y k3s-agent volvió a conectar sin más cambios.

umask 077; read -rs TSKEY; printf '%s' "$TSKEY" > /tmp/ts.key; unset TSKEY
sudo tailscale up --auth-key=file:/tmp/ts.key --hostname=gpu-node-01 --accept-dns=false
shred -u /tmp/ts.key

Lecciones:

  • En nodos, desactivar la expiración de clave o, mejor, darlos de alta con tag, que la desactiva por defecto.
  • En este clúster, k3s anuncia la IP 100.x como --node-ip y flannel usa tailscale0 vía --flannel-iface. Por eso, en el nodo WSL2, Tailscale corre dentro de la distro: la interfaz tiene que existir ahí, y el cliente de Windows no la crea dentro de WSL2.
Ojo con WSL2 La documentación oficial recomienda correr Tailscale solo en el host Windows, no dentro de WSL2. Si se instala dentro, tailscaled sube el MTU de la interfaz por defecto de 1280 a 1340 para poder funcionar, y no hay que tener Tailscale activo en Windows y en WSL2 a la vez: el tráfico de WSL2 que pase por el Tailscale de Windows deja de funcionar. Aquí se elige la variante dentro de la distro a conciencia, por el requisito de k3s.

08Checklist para dejar un nodo bien

  • Alta con la key de nodos: reusable, no efímera, preaprobada, con tag:k3s-node.
  • Expiración de clave desactivada (verificar en Machines).
  • --hostname fijo y --accept-dns=false.
  • Key pasada por file: o read -rs, nunca escrita en la línea de comandos.
  • tailscale ping control-plane responde, idealmente en directo y no por DERP.
  • kubectl get nodes -o wide muestra el nodo Ready con su IP 100.x.
