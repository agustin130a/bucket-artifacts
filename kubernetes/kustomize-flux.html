Código y versiones

Un repo GitOps que no se parece a ArgoCD

En ArgoCD lo habitual es una Application raíz que crea otras, cada una con un chart y su values.yaml. Este repo de Flux se organiza así:

Estructura del repo
cluster-core-config/<clúster>/        cluster-vars.yaml + Kustomizations de Flux con postBuild.substituteFrom
cluster-services/base/                applications/ (HelmRelease por servicio), values/, sources/, manifests/
                                      kustomization.yaml con configMapGenerator
cluster-services/cluster-services-dev/
                                      resources: [../base] + configMapGenerator con behavior: merge

Cada HelmRelease lee sus values de dos claves de un ConfigMap:

HelmRelease · valuesFrom
valuesFrom:
  - { kind: ConfigMap, name: values-mimir, valuesKey: base.yaml }
  - { kind: ConfigMap, name: values-mimir, valuesKey: env.yaml, optional: true }

Sobre los mismos archivos trabajan tres piezas, cada una en su turno: Kustomize, kustomize-controller (que además sustituye variables) y helm-controller. El taller reproduce esa estructura en ocho pasos, contra un clúster real.

1

El hash que rompe el HelmRelease sin dar ningún error

Kustomizehelm-controller
Qué pasaEl HelmRelease apunta a un ConfigMap que no existe y kubectl kustomize no avisa.
Qué hacergeneratorOptions.disableNameSuffixHash: true en la base.

configMapGenerator agrega un hash al nombre (values-podinfo-6bdg5tmhf7). Kustomize actualiza las referencias en los tipos que conoce, como un Deployment, pero no en un CRD como el HelmRelease. Existe configurations con nameReference para enseñárselo, pero un nombre fijo es más simple.

3

Flux sustituye todo el texto, incluidos los comentarios

kustomize-controller
Qué pasaUna variable que no existe queda como cadena vacía, sin error, también en comentarios.
Qué hacerCorrer flux envsubst --strict en local antes del PR.

postBuild.substituteFrom reemplaza ${VAR} sobre el YAML ya renderizado, incluido el contenido de los values dentro de un ConfigMap (docs). Como trabaja sobre texto, no distingue un comentario de un valor.

Cambiar los values no dispara el upgrade

helm-controller
Qué pasaEl ConfigMap cambió en el clúster, pero helm history sigue en la misma revisión.
Qué hacerLabel reconcile.fluxcd.io/watch: Enabled en generatorOptions.labels.

El HelmRelease no vigila sus ConfigMaps: los vuelve a leer en su interval. La label está entre las configuraciones recomendadas, y con Kustomize se pone una sola vez.

Qué es Kustomize

Renderizar el primer kustomization.yaml, sin clúster.

  • YAML copiado por entorno: cada cambio común se repite y los entornos divergen.
  • Helm: plantillas Go y un values.yaml por entorno. Solo se cambia lo que el autor del chart parametrizó.
  • Kustomize: YAML puro, sin plantillas. Una base y transformaciones en capas que pueden tocar cualquier campo.

Viene embebido en kubectl (kubectl kustomize, apply -k) desde Kubernetes 1.14 (docs), y Flux lo usa para renderizar cada path.

base y overlays

Una base y dos overlays (dev y prd) que la reutilizan con resources: [../base].

Kustomize renderiza la base y aplica encima el overlay (referencia):

  • namespace: fuerza el namespace de todo.
  • namePrefix: prefija los nombres y actualiza las referencias por nombre (configMapRef, serviceAccountName…).
  • commonLabels: agrega labels también a los selectores. Deprecado a favor de labels (docs).
  • patches: modifica recursos puntuales (docs).

YAML de Kubernetes, legibleLista de operaciones add/replace/remove
Combina listas por clave (name)Usa índices (/containers/0): frágil si cambia el orden

Regla práctica: strategic merge por defecto; JSON patch para borrar, para listas sin clave o para CRDs.

Generadores y sufijo hash

Generar ConfigMaps y Secrets, y ver qué hace el sufijo hash.

  • files: cada archivo es una clave (se renombra con clave=ruta).
  • envs: cada línea KEY=VALUE es una clave.
  • literals: KEY=VALUE inline (docs).

secretGenerator codifica en base64, pero no cifra. En un repo real se usa SOPS o External Secrets.

app/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: generators
resources:
  - namespace.yaml
  - deployment.yaml
configMapGenerator:
  - name: podinfo-config
    envs:
      - config/app.properties          # cada línea KEY=VALUE pasa a ser una clave
    literals:
      - PODINFO_UI_MESSAGE=version-1

  - name: podinfo-secret
    literals:
      - API_TOKEN=no-es-un-secreto-real   # dato de juguete: en serio, nunca en Git

behavior: merge y replace

La base genera values-podinfo con la clave base.yaml, y el overlay le agrega env.yaml al mismo ConfigMap.

Si el overlay declara un generador con el mismo nombre, behavior decide (docs):

  • create (default): falla por nombre duplicado.
  • merge: agrega claves; si la clave ya existe, la del overlay reemplaza el valor entero.
  • replace: deja solo el contenido del overlay.

configMapGenerator:

Flux: postBuild.substituteFrom

Flux corre kustomize build y después reemplaza ${VAR} en el texto, incluidos los values dentro de un ConfigMap (docs):

  • ${VAR} sin valor queda vacía, sin error.
  • ${VAR:=default} usa un valor por defecto.
  • $${VAR} queda como ${VAR} literal.
  • kustomize.toolkit.fluxcd.io/substitute: disabled la desactiva en un recurso.

flux envsubst hace lo mismo en local con las variables del entorno, y --strict falla si falta alguna (docs).

Errores típicos

  • Hash en nombres que usa un CRD. Quitar disableNameSuffixHash no da error, pero el HelmRelease apunta a un ConfigMap inexistente (paso 3).
  • ${...} ajenos a Flux (Alloy, Grafana, Loki): quedan vacíos sin aviso. Escaparlos con $${...}, también en comentarios (paso 5).
  • replace o create duplicado en el overlay. Se pierde base.yaml o falla el build (paso 4).
  • commonLabels sobre algo desplegado. Cambia selectores inmutables (paso 2).
  • Campos inmutables, como el template de un Job. Anotar ese recurso con kustomize.toolkit.fluxcd.io/force: enabled para que Flux lo recree, en vez de spec.force: true, que recrea cualquier recurso con conflicto (docs). Si viene de un chart, spec.upgrade.force en el HelmRelease, de forma temporal (docs).
  • Un upgrade que no llega. Falta la label reconcile.fluxcd.io/watch: Enabled (paso 7, fase C).

Validar antes del PR

Desde la raíz del repo GitOps. Los pasos 1 a 3 no necesitan clúster y sirven para CI.

  1. 1
    Errores de Kustomize, duplicados, rutassin clúster
    kubectl kustomize cluster-services/cluster-services-dev > render.yaml
  2. 2
    Variables faltantes, en modo estrictosin clúster
    # con las variables del clúster, si hay acceso:
export $(kubectl -n flux-system get cm cluster-vars -o go-template='{{range $k,$v := .data}}{{$k}}={{$v}} {{end}}')
flux envsubst --strict < render.yaml > final.yaml
  3. 3
    Los ${ que sobrevivieronsin clúster
    grep -n '\${' final.yaml
  4. 4
    Diferencias contra el clústercontra el clúster
    flux diff kustomization cluster-services --path ./cluster-services/cluster-services-dev

flux diff kustomization aplica el postBuild real; si no imprime nada, no hay diferencias (docs).
